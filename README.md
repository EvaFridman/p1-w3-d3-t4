# p1-w3-d3-t4
# Задача 4 — частичный индекс и индекс по массиву (GIN)

Два инструмента под конкретные ситуации. Частичный индекс покрывает не всю таблицу, а только нужное подмножество строк — когда запросы всегда идут с одним фильтром. GIN — индекс для колонок, где в одной ячейке много значений (массив, JSONB), по которым B-tree не умеет искать. Сдаёшь список с наблюдениями в md.

## Где работаешь

Схему и данные накатываешь один раз. В таблице есть колонка-массив тегов — для GIN.

## Входные данные

```sql
CREATE TABLE users (
  id         SERIAL PRIMARY KEY,
  email      VARCHAR(120) NOT NULL,
  name       VARCHAR(120) NOT NULL,
  status     VARCHAR(20)  NOT NULL,
  tags       TEXT[]       NOT NULL,
  created_at TIMESTAMPTZ  NOT NULL
);

INSERT INTO users (email, name, status, tags, created_at)
SELECT
  'user' || g || '@mail.io',
  'Имя' || g,
  (ARRAY['active','blocked','deleted'])[1 + (g % 3)],
  (ARRAY['sql','backend','frontend','devops','design'])[1 + (g % 5) : 2 + (g % 5)],
  now() - (g || ' minutes')::interval
FROM generate_series(1, 200000) AS g;
```

Здесь `status` — одно из трёх значений, `tags` — массив из пары тегов на строку.

Памятка по массивам (оператор на слайде показан не был): вхождение значения в массив проверяется оператором `@>`, например `WHERE tags @> ARRAY['sql']` — «у пользователя среди тегов есть sql». Именно такие запросы ускоряет GIN.

## Релизы

**Частичный индекс.**

1. `EXPLAIN ANALYZE` для `WHERE status = 'active'` без индекса — тип скана;
2. создай частичный индекс `CREATE INDEX idx_users_active ON users (email) WHERE status = 'active'` и сними план запроса, который фильтрует по `status = 'active'` и ищет по email — использует ли он частичный индекс;
3. сними план такого же поиска, но для `status = 'blocked'` — подходит ли частичный индекс под другой фильтр, и почему.

**GIN по массиву.**

4. `EXPLAIN ANALYZE` для `WHERE tags @> ARRAY['sql']` без индекса — тип скана и время;
5. создай `CREATE INDEX idx_users_tags ON users USING GIN (tags)` и снова сними план того же запроса — что изменилось;
6. сравни размер обычного B-tree по `email` и частичного индекса из релиза 2 (частичный меньше, потому что покрывает часть строк) — можно через `\di+` в psql или свойства индекса в DBeaver; записать, какой меньше.

## Что сдать

Файл `p1-w3-d3-t4.md`: каждый релиз — заголовок, блок SQL, строка-наблюдение (тип скана, `actual time`, а для релиза 6 — размеры индексов). Отдельной строкой — почему частичный индекс не подходит под фильтр `blocked` и почему для массива нужен GIN, а не B-tree.

## Ожидаемый результат

Частичный индекс задействуется только для запросов с тем же условием, по которому он построен: поиск при `status = 'active'` идёт по индексу (`Index Scan`), а такой же поиск при `status = 'blocked'` частичный индекс не использует — он этих строк не содержит, и план показывает `Seq Scan`. Частичный индекс заметно меньше обычного B-tree по той же колонке, потому что покрывает лишь подмножество строк. Запрос на вхождение в массив `tags @> ARRAY['sql']` без индекса выполняется перебором; после создания GIN-индекса план переходит на чтение по индексу и `actual time` падает — обычный B-tree так искать по массиву не умеет, потому что в ячейке несколько значений, а B-tree хранит одно упорядоченное. В сдаче зафиксированы планы, размеры и вывод, когда какой индекс уместен.
